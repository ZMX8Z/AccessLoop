# 四包协作与分支约定

本文件约定四包如何在同一仓库开发和集成。[项目约定](PROJECT.md)说明共同范围，各包目录提供启动与验收材料；HTTP 字段、状态、错误及示例统一见 [API_CONTRACTS.md](API_CONTRACTS.md)。本文是待执行约定，不表示已建立应用、提交 PR 或完成合并。

## 1. 固定分支与工作目录

| 工作包目录 | 主责 | 唯一工作分支 |
| --- | --- | --- |
| [A](../work-packages/a-frontend-map/README.md) | 视觉、公共组件、地图与路线前端 | `codex/a-frontend-map` |
| [B](../work-packages/b-frontend-reports/README.md) | 上报、报告、导出和后台自定义组件 | `codex/b-frontend-reports` |
| [C](../work-packages/c-backend-data-ai/README.md) | 数据、会话、照片、AI、报告和管理命令 | `codex/c-backend-data-ai` |
| [D](../work-packages/d-backend-routing/README.md) | 骨架、地理、路由、搜索、部署与总集成 | `codex/d-backend-routing` |

`dev` 是四包共同基线和唯一集成目标；所有包的 PR 均以 `dev` 为 base。`main` 仅用于发布；2026-10-18 用户已授权的本次同步见第 6 节。D 是集成负责人。

同一仓库不等于共用同一个工作目录。每人使用独立 clone 或 managed worktree；已有适合本包的工作目录就复用。不得让多个会话在同一路径并发切换分支；同一分支也不同时检出到两个 worktree。

进入任何开发会话，先检查实际工作目录、当前分支和未提交改动：

```sh
pwd
git status --short
git branch --show-current
git worktree list
git branch --list 'codex/a-frontend-map'
git branch --remotes --list 'origin/dev' 'origin/codex/a-frontend-map'
```

以上以 A 为例，其他人替换为自己的固定分支。若本包分支已在另一个工作目录检出，前往该目录复用；若当前目录有未提交改动，先保留并确认归属，不自动 stash、reset 或丢弃。需要隔离时优先创建 managed worktree，并使用工具返回的目录。

在确认属于自己的、无冲突的工作目录后更新远端信息：

```sh
git fetch origin
```

随后按实际状态只选择一种：

```sh
# 本地分支已存在，且没有在其他 worktree 检出
git switch codex/a-frontend-map
```

```sh
# 仅远端有本包分支
git switch --track -c codex/a-frontend-map origin/codex/a-frontend-map
```

```sh
# 本地与远端均无本包分支，才从共同基线创建
git switch -c codex/a-frontend-map origin/dev
```

网络或凭据不可用时，继续使用已确认的本地 `dev` 和现有代码，记录基线提交及远端未核对的限制；没有执行成功就不能声称已 fetch、push 或创建 PR。本地也没有共同基线时，先记录缺项，不随意选取其他分支替代。

## 2. 阶段交付与同步

四包持续使用各自固定分支，不为每个阶段增加长期分支。按以下顺序交付可独立检查的阶段 PR：

0. D 先检查本套权威文档和四包材料是否已进入共同基线；若仍是当前工作目录中的未提交文档，确认归属后在自己的固定分支提交为文档准备阶段 PR 并合入 dev。所有成员从包含该文档提交的 dev 起步；新 worktree 不会自动带入原目录未提交文件，不能假定材料已随分支复制。

1. D 先交付可启动骨架、最小契约和 fixture，经检查后进入 `dev`；随后明确将 Payload 配置、Collections、迁移及仓储交接给 C。
2. C 从新的 `dev` 同步骨架，尽早交付基础仓储与会话接口；P0 基础交付包含预设通道表/迁移、将 D 实测交接的初始通道数据落库、稳定 ID 与版本读取，供 D 的 passages 接口及 A/B 的预设通道流程使用。P1 在此基础上增加运营配置命令、通道变更增版和影响检查。A 同步骨架并尽早交付公共请求工具、页面外壳和地图组件接口。两者分别提交阶段 PR 至 `dev`。
3. B 同步公共组件，D 同步基础仓储；各包继续 P0 双线、个人避让闭环，再完成 P1 搜索、公共管理和集成验收。按可检查阶段持续更新 PR，不等待整包结束才交付基础依赖。

依赖尚未进入 `dev` 时，可按已确认契约和清楚标识的 fixture 继续独立部分；真实联调和供应商验证仍须完成。不要让 C 等 D 整包、D 等 C 整包或 B 等 A 整包形成循环等待。

每次开始新阶段、依赖已合入或准备交付时，在本包分支同步：

```sh
git fetch origin
git merge origin/dev
```

先检查未提交改动和正在进行的 merge；冲突由本包负责人结合共享文件负责人解决，再运行受影响检查。已共享分支使用 merge 同步，不 rebase、不强推重写历史。阶段合入后保留固定分支供后续工作继续使用。

子 agent 的结果由父包负责人整合、自检并留在该包固定分支。确需短期子分支时，在父分支名后加 `-<task>`，例如 `codex/a-frontend-map-search`；先合回父包，再由父包 PR 进入 `dev`，不建立第五条集成工作流。

## 3. 共享文件与契约变更

| 共享内容 | 负责人 | 其他包的协作方式 |
| --- | --- | --- |
| `package.json`、lockfile、构建/部署配置、环境变量示例 | D | 提交明确依赖或配置需求，由 D 整合 |
| Payload 配置、Collections、迁移、事务与业务仓储 | C；D 骨架阶段后交接 | D 通过仓储接口使用数据；B 交接组件，由 C 注册挂载 |
| 公共错误、地点、通道、路线、搜索和地理契约 | D | A/B/C 校验消费方式，共同确认变更 |
| 上传、AI、报告、确认、管理命令和公开字段契约 | C | 与 D 的地理、版本和预算接口对齐，A/B 校验调用 |
| 公众外壳、全局样式、公共请求工具、共享地图组件 | A | B 在所属功能中接入；共享修改先交接给 A |
| 上报/报告 UI、纯展示导出模板、自定义管理组件 | B | C 负责正式挂载、服务端权限和数据接入 |
| 权威文档、根 `AGENTS.md`、README 与 API 文档整合 | D | C 维护其接口内容，A/B 核对用法 |

需要修改其他包或共享文件时，先说明文件、原因和调用方影响，由负责人协调归入一个明确的变更；不让双方同时维护同一份实现。

API 变更先在唯一的 [API_CONTRACTS.md](API_CONTRACTS.md) 中由相关负责人确认，再同步运行时 Schema、推导类型、fixture 和所有调用方，并在同一交付中检查一致性。Schema 是契约的实现；遇到文档与代码冲突时，先澄清并修正契约，不能自行选择现有代码覆盖已确认语义。工作包交接文档只引用该契约，不复制一套可独立演进的 API 定义。

## 4. 最小内部交接

这些是包间边界，具体类型与字段仍以共享契约及后续实现为准。

| 交接 | 最小约定 |
| --- | --- |
| A → B 地图/位置选择 | 组件接收位置、路线、预设通道及预览几何；输出位置和共享 `PassageRef`。B 持有表单状态，组件不自行保存报告。A 交付导出路径、props/events 与使用示例。 |
| A → B 请求工具 | 统一会话初始化、成功/错误解包与过时请求处理；B 不另建一套请求或会话协议。 |
| B → C 管理组件 | B 交付明确导出、输入和所需命令；C 完成 Payload 注册、权限、数据与实际 `/admin` 挂载，双方共同验证入口。 |
| B → C 导出模板 | 无浏览器依赖的纯展示模板及打印样式；C 在授权导出入口复用，并安全处理用户和 AI 文本。 |
| C → D 仓储 | 提供会话/区域、有效避让一致快照、routeRef、缓存、预算原子预留和摘要读取；统一 Payload 连接与事务上下文。基础仓储不导入 ORS/GLM 服务。 |
| D → C 地理/预算 | 提供通道引用验证、预览/确认共用几何、公共几何及区域影响验证、分服务预算门禁。网络请求放在数据库事务外；依赖方向为业务服务 → 门禁 → 仓储。 |

交接应写明可用阶段、输入输出、使用示例和尚未验证的外部条件。内部接口调整也要同步提供方与消费方，避免另建数据库连接或两套几何算法。

## 5. PR、验收与合并

- 提交前在本包分支同步 `origin/dev`，完成相关静态检查、主流程及必要失败回归；真实接口未验证则如实记录。检查命令以实际应用脚本为准，不预先宣称通过。
- 先检查本包是否已有目标为 `dev` 的开放 PR；有则更新，无则创建。PR 写明本次阶段、变更、契约/依赖影响、检查证据、阻塞和交接入口，不能把 P0 阶段写成整包 P0/P1 完成。
- 交接见 `docs/handoffs/wp-a.md` 至 `wp-d.md`，技术验收见 `docs/acceptance/wp-a.md` 至 `wp-d.md`。验收记录必须标出 PR/head SHA、目标 `dev` 的 base SHA 和证据所对应提交；可用 `git rev-parse HEAD`、fetch 后的 `git rev-parse origin/dev` 获取。
- 发生新提交、解决冲突或目标 `dev` 前移时，评估差异并复验失败项及受影响主流程；不能将旧 head/base 的通过结论直接套用。可复用同一提交上可核对的共享证据。
- A/B/C 提供技术验收通过的阶段 PR；D 对自己的阶段 PR 同样完成技术检查，并作为唯一集成人，按骨架 → 基础仓储/公共组件 → 后续功能依赖顺序串行合入 `dev`。用户已授权各包最终集成至 `dev`，常规阶段合并无需重复询问；平台保护实际要求人工审批时，才报告具体所需动作。
- 阶段 PR 使用保留历史的 merge commit，合入后保留四个固定分支供后续阶段使用。D 通过 PR 平台合并；需要本地集成时使用专用的 dev 工作目录，dev 只接收已检查的合并，不直接开发功能。
- 每次合入后记录集成 SHA，D 检查必要构建、类型及受影响闭环；在同一集成提交统一完成真实 P0/P1 总验收。已有可靠证据且未受影响的场景无需全量重复，fixture 或降级通过也不能代替真实能力验收。
- 人工按[总验收约定](ACCEPTANCE.md)和各包 `MANUAL.md` 检查页面功能、界面和文案；技术检查与证据由 AI 完成，不要求人工审查代码、运行命令或查库。

四包最终全部进入 `dev` 才算完成本轮开发集成；发布到 `main` 按明确授权执行，本次范围见第 6 节。本文件定义执行规则，不代表已创建分支、推送或合并；这些动作在工作包实际执行时完成。
